NexTT — подсказки для разработчика

Документ для тех, кто периодически вносит изменения в программу. Здесь всё, что нужно помнить: где менять прайсы, как собрать новую версию, где включать логирование.

1. Введение

Этот документ — ваша памятка. Вы не обязаны помнить всё, что описано ниже. Просто откройте этот файл, когда нужно что-то сделать, и следуйте инструкциям шаг за шагом.

📌 Для кого: для человека, который периодически обновляет программу NexTT.
💡 Совет: Открывается любым браузером. Сохраните файл в папке с проектом.

2. Где что лежит (полные пути)

Все пути указаны относительно корневой папки проекта — это папка, в которой лежат папки nextt/ и resources/.

📁 Корень проекта: C:\Projects\...\NexTT\

Важные файлы и папки

💡 Запомните: ресурсы (Excel-файлы) лежат в папке resources/. Если замените их здесь, они попадут в новую сборку.

3. Как обновить прайс-лист радиаторов

Когда нужно: изменились цены, мощность или вес радиаторов. Файл называется Мономатрица.xlsx.

Пошаговая инструкция:

  1. Откройте папку корень проекта.
  2. Зайдите в папку resources/.
  3. Найдите файл Мономатрица.xlsx.
  4. Замените его на новый файл (перетащите или скопируйте с заменой).
  5. Важно: Если вы будете собирать EXE, новый файл автоматически попадёт в сборку.
📌 Примечание: Можно открыть файл Excel, отредактировать прямо в нём и сохранить. Главное — сохранить то же имя файла.
⚠️ Не переименовывайте файл! Программа ищет файл с точным именем Мономатрица.xlsx.

4. Как обновить каталог оборудования

Когда нужно: добавились новые котлы, бойлеры, дымоходы или запчасти. Файл называется Все_категории.xlsx.

Пошаговая инструкция:

  1. Откройте папку корень проекта.
  2. Зайдите в папку resources/.
  3. Найдите файл Все_категории.xlsx.
  4. Замените его на новый файл (или отредактируйте существующий).
  5. Важно: В файле должны быть колонки: Артикул, Наименование, Цена, Иерархия (категория).
💡 Подсказка: Если вы добавляете новые позиции, убедитесь, что в колонке «Иерархия» указана правильная категория (запчасти, котлы, дымоходы и т.д.).

5. Как выпустить новую версию программы

Когда нужно: вы обновили прайсы или добавили новые функции — нужно, чтобы пользователи узнали об этом.

5.1. Логика работы версий (как это работает)

🎯 Зачем вообще нужна проверка обновлений?

Когда вы выпускаете новую версию программы, пользователи должны об этом узнать. Для этого программа при каждом запуске сравнивает свою версию с версией на GitHub. Если на GitHub версия новее — появляется окно с предложением обновиться.

📊 Что где хранится?

1
Внутри программы (на вашем компьютере)
Файл nextt/utils/update_checker.py содержит два значения: 
CURRENT_VERSION = "2.1"      # ← текст, который увидит пользователь
CURRENT_VERSION_CODE = 21     # ← число, с которым программа сравнивает

Что это значит: программа «знает», что её версия — 2.1 (показывать людям) и её числовой код — 21 (использовать для сравнения).

2
На GitHub (в интернете)
Файл version.json содержит такие же два значения, но для самой последней версии: 
{
    "version": "2.2",
    "version_code": 22
}

Что это значит: в интернете лежит информация, что последняя доступная версия — 2.2 с кодом 22.

⚙️ Как происходит сравнение (по шагам)

1
Пользователь запускает программу версии 2.1 (код 21).
2
Программа скачивает файл version.json с GitHub.
3
Программа смотрит на version_code из интернета (22).
4
Программа сравнивает: 22 > 21? ДА → значит, есть новая версия.
5
Программа берёт "version" из интернета (2.2) и показывает окно: «Доступна новая версия 2.2».
💡 Почему нужен именно числовой код?
Компьютер плохо сравнивает текст "2.10" и "2.2" — по буквам "2.10" меньше, чем "2.2", потому что "1" меньше "2". А числа 210 и 22 сравниваются правильно: 210 > 22. Поэтому мы используем числовой код для сравнения, а текст — только для показа пользователю.

✅ Примеры правильного сравнения

✔ Программа 2.1 (код 21), на GitHub код 22 → 22 > 21 → обновление есть
✔ Программа 2.5 (код 25), на GitHub код 30 → 30 > 25 → обновление есть
✔ Программа 3.0 (код 30), на GitHub код 30 → 30 = 30 → обновления нет (версии одинаковые)

❌ Ошибки — что будет, если неправильно указать версии

✖ В программе код 22, на GitHub код 21 → программа думает, что у неё версия новее, обновление не покажет
✖ В программе код 21, на GitHub код 21 (но версия 2.2) → программа не увидит обновление, потому что коды одинаковые
✖ Забыли обновить version.json на GitHub → программа никогда не покажет обновление
⚠️ Главное правило: код новой версии должен быть строго больше кода предыдущей версии. Нельзя из 2.1 сделать 2.2 с кодом 21 — программа не увидит разницы!

📐 Как определить код для новой версии

Версия для пользователяКакой код писатьПояснение
2.1 → 2.221 → 22Убрали точку, увеличили на 1
2.9 → 2.1029 → 210Убрали точку, 2.10 = 210
2.10 → 2.11210 → 211Просто увеличили на 1
2.99 → 3.0299 → 30Переход на новый диапазон, код сбрасывается
💡 Простой способ: уберите точку из версии и получите код. 2.1 → 21, 2.2 → 22, 3.0 → 30. Главное — следите, чтобы код увеличивался.

5.2. Что менять в программе (локально)

📄 Файл: nextt/utils/update_checker.py

Откройте этот файл в любом текстовом редакторе (Блокнот, Notepad++, VS Code). Найдите и измените эти строки:

update_checker.py — строки для изменения
CURRENT_VERSION = "2.2"        # ← новая версия (например, 2.2) — что увидят пользователи
CURRENT_VERSION_CODE = 22       # ← код версии (например, 22) — для сравнения компьютером

Что здесь происходит: вы сообщаете программе, что её собственная версия теперь 2.2 (текст) и код 22 (число).

5.3. Что менять на GitHub (в интернете)

🌐 Файл на GitHub: https://github.com/e-laggartt/NexTT/blob/main/version.json

Зайдите на GitHub, откройте этот файл, нажмите «Редактировать» (карандаш). Измените содержимое:

version.json — пример
{
    "version": "2.2",
    "version_code": 22,
    "download_url": "https://b24.engpx.ru/~kMmVo",
    "release_date": "2026-06-01",
    "whats_new": [
        "Обновлён прайс-лист",
        "Добавлены новые котлы",
        "Исправлены мелкие ошибки"
    ]
}

Что здесь происходит: вы размещаете в интернете информацию о том, что последняя версия — 2.2 с кодом 22. Когда пользователи запустят программу, она скачает этот файл, увидит код 22 и сравнит со своим кодом.

⚠️ Важно: version_code в этом файле должен совпадать с тем, что вы написали в update_checker.py! И оба должны быть больше предыдущих значений.
📌 Процесс целиком: вы меняете версию в программе → собираете новый EXE → выкладываете EXE на Битрикс → обновляете version.json на GitHub. Когда пользователь запустит старую версию, она скачает новый version.json, увидит, что код стал больше, и покажет окно «Доступна новая версия 2.2».

6. Как собрать EXE-файл (build.py)

Сборка — это превращение папки с кодом в один исполняемый файл .exe. Запускается через build.py.

Что нужно сделать перед сборкой:

  1. Убедиться, что все файлы resources/ обновлены.
  2. Если выпускаете новую версию — изменить CURRENT_VERSION в update_checker.py.
  3. Выбрать тип сборки (обычная или dev).

6.1. Обычная сборка (для пользователей)

В этой сборке нет консоли, нет отладочных сообщений.

  • Откройте командную строку в корне проекта.
  • Введите команду: python build.py
  • Дождитесь окончания (появится надпись «Готово!»).
  • Готовый EXE лежит в папке dist/.
Команда для обычной сборки
python build.py

6.2. Dev-сборка (для тестирования)

В этой сборке видна консоль и все отладочные сообщения. Не распространяйте среди пользователей!

  • Откройте файл build.py в текстовом редакторе.
  • Найдите строку "--windowed" и удалите её (или закомментируйте).
  • Измените имя выходного файла: "--name=NexTT_dev" (чтобы не перепутать).
  • Запустите python build.py.
💡 Подсказка: Dev-версия показывает все ошибки в консоли — очень удобно для поиска проблем.

7. Как включить или выключить логирование

Логирование — это подробные сообщения о работе программы (что происходит, какие ошибки). Обычным пользователям это не нужно, но разработчику помогает отлаживать.

📄 Файл: nextt/app.py

Откройте файл, найдите строку:

app.py — настройка логирования
setup_logger(level="WARNING", log_file=None)   # ← меняйте здесь

Какие значения можно ставить:

ЗначениеКогда использовать
"WARNING"Для обычной сборки (пользователи). Только ошибки.
"ERROR"Только критические ошибки. Ещё тише.
"INFO"Для разработчика. Подробные сообщения.
"DEBUG"Максимально подробно. Только для отладки.
📌 Запомните: перед финальной сборкой для пользователей ставьте "WARNING".

8. Как включить экспериментальную кнопку «Вставить из буфера»

Это новая функция, которая пока тестируется. По умолчанию она выключена.

📄 Файл: nextt/experimental/paste_handler.py

Откройте файл, найдите в самом начале:

paste_handler.py — флаг функции
EXPERIMENTAL_ENABLED = True   # ← True = включена, False = выключена

Когда что ставить:

  • True — кнопка «Вставить из буфера» появляется в меню. Включите, если хотите протестировать.
  • False — кнопка скрыта. Используйте для финальной сборки.
⚠️ Важно: Функция экспериментальная, могут быть ошибки. Не включайте в финальной версии без тестирования.

9. Чек-лист выпуска новой версии

Перед тем как разослать обновление партнёрам, проверьте всё по списку.

  • Обновлён Мономатрица.xlsx (если изменились цены)
  • Обновлён Все_категории.xlsx (если добавилось оборудование)
  • Изменён CURRENT_VERSION и CURRENT_VERSION_CODE в update_checker.py
  • Обновлён файл version.json на GitHub (версия, дата, список изменений)
  • Выключена экспериментальная кнопка (EXPERIMENTAL_ENABLED = False)
  • Уровень логирования установлен в "WARNING"
  • Собран EXE через python build.py
  • Проверено, что EXE запускается и работает
  • Старая версия видит обновление и показывает диалог
  • Новый EXE загружен на Битрикс по ссылке из download_url

10. Частые проблемы и решения

❓ Программа не видит обновление

Причины: не совпадает version_code в update_checker.py и version.json. Или файл version.json недоступен.

Решение: проверьте, что version_code в обоих файлах одинаковый и больше предыдущего. Откройте ссылку на version.json в браузере — должен открываться JSON.

❓ Ошибка SSL при проверке обновлений

Причина: проблема с сертификатами GitHub.

Решение: в коде update_checker.py уже есть обход этой ошибки. Если проблема повторяется — временно отключите проверку обновлений, установив VERSION_URL = "".

❓ EXE не запускается или сразу закрывается

Решение: соберите dev-версию (с консолью). Запустите её — ошибка будет видна в консольном окне.

❓ Не работает кнопка «Вставить из буфера»

Причина: экспериментальная функция выключена.

Решение: откройте paste_handler.py и установите EXPERIMENTAL_ENABLED = True, затем пересоберите EXE.

💡 Главный совет: Если что-то пошло не так — соберите dev-версию с консолью и смотрите, что пишет программа. Это самый быстрый способ найти проблему.
